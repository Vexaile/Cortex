## P1. `openWorkspace` is an incomplete reset of workspace-scoped state
**Merges #1, #21 (simParts), #2, #22 (tabs), #3 (selectedFqbn), #26 (running/simRunning).** One root cause: `openWorkspace`'s `set()` at `useStore.ts:412-420` enumerates seven keys (`workspaceRoot, workspaceName, tree, childrenCache, expanded, diagnostics, output`) and every other piece of workspace-scoped state was added to the store without being added here. Five separate symptoms, one edit block.

**Defect:** Opening a second folder carries the previous project's circuit, tabs, board target, and live processes into it, and the carried circuit is then written to the new project's disk.

Verified consequences:
- `simParts` is never reset; `loadDiagram` (796) early-returns at **803** on a workspace with no `.cortex/diagram.json` and also silently no-ops when `data.parts` is not an array (807 `if` with no `else`). `saveDiagram` (786) then writes `get().simParts` -- project A's rig -- into B's `diagram.json` at **794**. Default parts (`led-13`, `btn-2`, 368-371) become unreachable forever.
- `tabs`/`activePath` are never cleared, while `watchStart` (421) repoints `fsService`'s confinement root (`fsService.ts:118`). Ctrl+S on a carried tab throws `Refused: path is outside the open workspace` inside `writeFile`; `saveActive` (529-539) has no `try/catch` and all four call sites discard the rejection.
- `selectedFqbn: cfg.boardFqbn || get().selectedFqbn` (**1045**) has no global default behind the `||`, unlike its siblings at 1042-1044, so it resolves to the last project's board and `refreshBoards`' autodetect (1068) is skipped.
- `running`/`simRunning` survive, and both entry guards return silently (`startSim` 642, `runActive` 850, `verifyBoard` 1084, `uploadBoard` 1108). `loop()` never terminates, so `simRunning === true` is the default state when a user opens a folder, not a race.

**Files that must change:**
- `src/renderer/src/store/useStore.ts`
  - Hoist `368-371` into an exported `DEFAULT_SIM_PARTS` so the initializer and the reset share one source.
  - `409-420`: `await get().stopRun(); await get().stopSim()` before `watchStop`; add to the `set()`: `tabs: [], activePath: null, reveal: null, simParts: DEFAULT_SIM_PARTS, simSerial: [], simInputs: {}, simPinStates: {}, simPinPwm: {}, simPinModes: {}, simWiring: null, serialCarry: '', running: false, runId: null, runPhase: 'idle', runAction: null, simRunning: false, simRunId: null, lastExitCode: null`.
  - `435`: `await get().loadDiagram()` (not `void`), so the canvas never paints the previous project's parts.
  - `803` and `807`: make `loadDiagram` authoritative -- both miss paths `set({ simParts: DEFAULT_SIM_PARTS })` instead of returning.
  - `1045`: `selectedFqbn: cfg.boardFqbn || ''`.
  - `529-539`: wrap the `writeFile` in `try/catch` and push failures into `output` + `bottomView: 'output', bottomVisible: true`, mirroring `runActive`'s reporting at 886-893.
- Callers need no change (the fix is inside the action), but confirm all six reach it: `App.tsx:97`, `Welcome.tsx:40`, `Welcome.tsx:50`, `Welcome.tsx:75`, `TitleBar.tsx:83`, `FileExplorer.tsx:98`, `CommandPalette.tsx:63`.
- `saveActive`'s four discarding call sites stay as-is once the action reports its own failure: `App.tsx:117`, `TitleBar.tsx:102`, `CodeEditor.tsx:146`, `CommandPalette.tsx:56`. Also check the four internal awaits that sit outside their `try`: `useStore.ts:681` (startSim), `861` (runActive), `1087` (verifyBoard), `1137` (uploadBoard).
- `src/main/services/fsService.ts:118` -- no change, but it is the other half of the contract; note it in the reset comment.

**Regression test: `test/workspaceReset.test.ts` (new).** Test env is `node` with no jsdom, so extract the reset into a pure exported `workspaceScopedReset(): Partial<State>` and assert it contains every key the store declares as workspace-scoped. That makes the test possible *and* makes the next added key fail loudly.

## P2. `SerialClass` reimplements `Print` as a generic template instead of Arduino's overload set
**Merges #14 (ambiguous overloads), #15 (byte prints as char), #16 (float formatting), #18 (lowercase hex).** One root cause at `arduinoShim.ts:139-140`: `template <class T> print(T v)` with `o << v` catches everything Arduino handles with typed overloads.

**Defect:** Standard Arduino print idioms either fail to compile or print differently than the board.

- **Compile error (critical):** the only 2-arg overloads are `(long,int)`, `(int,int)`, `(unsigned int,int)` at 141-146. `Serial.println(voltage, 2)` and `Serial.println(millis(), DEC)` make all three viable at identical conversion rank. Verified: `error: call of overloaded 'println(float&, int)' is ambiguous`. Because `simService.ts:51` injects `#line 1 "<user file>"`, the error is squiggled onto the user's own correct `.ino`.
- `byte` is `uint8_t` (line 25), so `o << v` inserts a **character**. A byte of 10 injects a newline and splits `__buf` into a spurious extra `@serial` line.
- Floats print `1e+06` / `1` where the board prints `1000000.00` / `1.00`.
- `const char* d = "0123456789abcdef"` (**126**) prints `ff` where the board prints `FF`.

**Files that must change:**
- `src/main/services/arduinoShim.ts`: add `#include <iomanip>`; add `print/println(double v, int digits)` (fixed, `setprecision(digits)`); add `print/println(double v)` defaulting to 2 fixed decimals; add `print/println(unsigned long, int)` and `print/println(unsigned long long, int)` (covers `size_t` on Win64); add one-arg `unsigned char`/`signed char` overloads routing to `__base(v, v, DEC)` -- do **not** broaden the template and do **not** touch `char`, which must stay a character; change **126** to `"0123456789ABCDEF"`.
- `docs/SIMULATOR.md:17-18` -- the `Serial.*` coverage line should state what is and is not mirrored.
- `examples/sim/rgb_fade.ino`, `examples/blink/blink.ino` -- add a float/base print so the new behavior is exercised by shipped code.

**Regression test: `test/arduinoShim.test.ts` (new).** `ARDUINO_SHIM` is an exported string; write it plus a fixture sketch to a temp dir, compile with host `g++`, run, assert stdout. Gate with `it.skipIf(!hasGpp)`. Cases: `println(3.14159)` -> `3.14`, `println(1.0)` -> `1.00`, `println(1000000.0)` -> `1000000.00`, `println(voltage, 2)` compiles, `println(millis(), DEC)` compiles, `byte b = 200; println(b)` -> `200`, `println(255, HEX)` -> `FF`. This one test file covers P2, P8, and P12.

## P4. `loadDiagram` restores saved ids but never reseeds `simCompCounter`
**#6.** `let simCompCounter = 0` (`useStore.ts:70`) is per-session module state. `addPart` mints `` `${type}-${++simCompCounter}` `` (**731**). `loadDiagram` ends at `set({ simParts: parts })` (**820**) without advancing it. The `fs:exists` probe and the v1->v2 migration both landed here; the reseed did not.

**Defect:** After restart, the next added part can collide with a restored id, and every mutator matches by id with a whole-array `map`/`filter` -- so a duplicate id broadcasts: `movePart` 743, `rotatePart` 746, `setPartColor` 749, `removePart` 753, `attachWire` 766. Dragging one LED moves both; deleting one deletes both. React keys on it at `SimCanvas.tsx:452`.

Collision requires the new part's **type and ordinal** to both match a restored part, which is exactly what happens to a user who adds LEDs, saves, restarts, and adds another LED. Additionally: the default parts use a *different* id scheme (`led-13`, `btn-2` = `${type}-${pin}`, line 369-370) than `addPart`'s (`${type}-${counter}`), so the 13th LED added in a fresh session collides with the default even without any load.

**Files that must change:**
- `src/renderer/src/store/useStore.ts`: mint ids from `crypto.randomUUID()` in `addPart` (**731**) and `startSim` (**682**, which shares the same counter), which fixes the load collision, the default-part collision, and the shared-counter coupling in one move. If the readable `led-1` format must stay, then instead reseed after building `parts` in `loadDiagram` (before 820) *and* renumber the defaults at 369-370 to match the mint scheme.

**Regression test: `test/simIds.test.ts` (new).** Assert `addPart` after a `loadDiagram` of a saved `led-1` never produces a duplicate id. Requires the id minting to be an exported pure helper.

## P5. A cross-compiler satisfies the simulator's "host C++ available" guard
**#27.** Three files disagree about what `kind: 'cpp'` means.

- `toolchainService.ts:25-26` classifies `arm-none-eabi-g++` and `avr-g++` as `kind: 'cpp'` (verified).
- `useStore.ts:829-833` auto-selects the first available `kind === 'cpp'` as `compiler`.
- `useStore.ts:652` guards `startSim` with the same predicate, so the helpful "No C++ compiler found / winget install MSYS2.MSYS2" remedy at 654-665 is skipped.
- `simService.ts:59-61` then discards the choice: `isAllowedCommand('avr-g++')` is true (`src/shared/security.ts:16-19`) but the base-name test rejects it, so it silently substitutes `'g++'` and spawns it.

Nothing anywhere verifies that `g++` or `clang++` specifically is on PATH. The user gets `spawn g++ ENOENT` in the serial pane -- the exact failure the comment at 645-647 says the guard prevents -- while ToolchainsPanel shows a green check under a group labelled "C / C++".

**Files that must change:**
- `src/shared/` (new predicate, e.g. in `security.ts` or a `toolchains.ts`): export `isHostCpp(command)` = allowlisted **and** basename in `['g++','clang++']`.
- `src/main/services/simService.ts:59-61`: use it; and stop silently substituting -- emit a system line naming the substitution or fail with the remedy text.
- `src/renderer/src/store/useStore.ts:652`: guard on `toolchains.find(t => t.available && isHostCpp(t.command))`.
- `src/renderer/src/store/useStore.ts:829`: same predicate, so `compiler` is never auto-set to something the sim cannot spawn.
- `src/main/services/toolchainService.ts:25-26`: give the cross-compilers their own kind (`'embedded'`) so ToolchainsPanel stops telling the user their C++ is fine.
- `src/renderer/src/components/ToolchainsPanel.tsx:8`: add the `KIND_LABEL` entry for the new kind.
- Related precedence bug to check while here: `useStore.ts:1027` (`compiler: s.defaultCppCompiler || get().compiler`) can overwrite what `detectToolchains` picked, depending on load order.

**Regression test: `test/simGuard.test.ts` (new).** Pure: assert `isHostCpp` accepts `g++`/`clang++`/absolute paths to them and rejects `arm-none-eabi-g++`/`avr-g++`, and that the store guard and `simService` import the *same* symbol.

## P6. Serial session state outlives the serial session

- `serialCarry` is read at **981** and rewritten at **993**. Grep confirms exactly one clearer: `clearSerial()` (**996**), wired only to BottomPanel's trash button. Not cleared by `toggleSerial`'s close branch (965-966), its open branch (967-969), `uploadBoard`'s pre-flash close (1132-1136), or `App.tsx:61-66`'s `onSerialStatus`. Result: the tail of the old session is glued onto the first line of the new one, and `extractSeries` puts the fused line on the plot. `SerialMonitor.tsx:111` also keeps rendering the carry after Disconnect.

Once stranded true, **any** later upload started with the monitor closed skips the re-arm at 1132 yet still fires `void get().toggleSerial()` at 919, seizing a port the user deliberately freed.

**Files that must change:**
- `src/renderer/src/store/useStore.ts`: `serialCarry: ''` in both branches of `toggleSerial` (966, 969) and in `uploadBoard`'s close (1134); clear `reopenSerialAfterUpload = false` in `stopRun` (899) and `uploadBoard`'s catch (1153). - `src/renderer/src/App.tsx:61-66`: clear `serialCarry` when `s.open` flips (this is the unplug path).
- `src/renderer/src/components/SerialMonitor.tsx:111`: stop rendering the carry when `!serialOpen`.

## P8. Serial output with no trailing newline is never emitted
**#17.** `__flushLines` (`arduinoShim.ts:115-122`) only drains `__buf` up to a `'\n'`. `SerialClass` (113-151) has no destructor and there is no `atexit`, so `main()` returning (`simService.ts:34`) destroys the residue unemitted. `simService.ts:144-147`'s `child.on('close')` has the same gap at the other end: it calls `exit()` without draining the `buf` accumulated at 133.

**Defect:** `void setup() { Serial.begin(9600); Serial.print("Ready..."); }` prints nothing for the entire run. Any progress line or prompt built with repeated `print()` is invisible until a newline arrives, and lost forever if the sketch exits first.

**Files that must change:**
- `src/main/services/arduinoShim.ts`: add `~SerialClass()` that emits a non-empty `__buf` as a final `@serial` line and flushes.
- `src/main/services/simService.ts:144-147`: drain the residual `buf` in the close handler before `exit()`.
- `src/shared/simProtocol.ts:9-11` + `docs/SIMULATOR.md:18`: if live unterminated prompts matter, this needs a `@serialpart <text>` directive; line buffering is what hides them today. Decide and document, do not leave the protocol comment claiming full coverage.

**Regression test:** add the unterminated-print case to `test/arduinoShim.test.ts` (P2).

## P12. Pin-level API contract drift in the shim
**Merges #19 (`digitalRead`), #20 (`analogWrite`).** Same root cause: the shim passes raw values where Arduino / its own protocol define a range.

- `arduinoShim.ts:78` `digitalRead` returns `__sim_in[p & 127].load()` verbatim. The same slot is written by analog sliders: `SimCanvas.tsx:331` -> `setSimInput(pins.sig, 0..1023)` -> `useStore.ts:784` `@in` -> shim stdin thread stores unmodified at **61**. Arduino specifies `digitalRead` returns exactly HIGH or LOW. (Note: the finding's "512 reads HIGH on a real board" is electrically wrong -- 512/1023 is in the indeterminate band. Normalize to 0/1 anyway, because returning 512 from `digitalRead` violates the contract regardless of where the threshold sits. Use a documented threshold and say so in the comment.)
- `arduinoShim.ts:79` `analogWrite` emits `v` raw, so `@pwm 9 300` violates the shim's own protocol contract (`simProtocol.ts:9` "@pwm <pin> <0-255>", echoed at `docs/SIMULATOR.md:18`), and `parseSimLine` (24-31) range-checks nothing. `SimCanvas.tsx:78` (`sig.value / 255`) and `147` (`(sig.value/255)*180 - 90`) then compute out of range. The clamping convention already exists on the input path (`SimCanvas.tsx:138, 157, 167`) and was simply not applied on the output path.

**Files that must change:**
- `src/main/services/arduinoShim.ts:78`: normalize to 0/1 against a named threshold constant.
- `src/main/services/arduinoShim.ts:79`: clamp to 0..255 to match the 8-bit register and the protocol.
- `src/shared/simProtocol.ts:24-31`: range-check `@pwm` and `@pin` rather than trusting the producer.
- `test/simProtocol.test.ts`: extend for the range check. `test/arduinoShim.test.ts` (P2) covers the emitter side.
